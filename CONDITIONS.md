### Architecture mapping (golden_core)

The design below describes `ConditionCommon` and `ConditionContainer` as Rust structs.
In this codebase they are expressed via the `#[children(...)]` node macro instead:

- **`ConditionCommon`** → shared `invert`, `validation_delay_ms`, `invalidation_delay_ms` children on each condition node type. The `enabled` toggle is the node's native enable/disable mechanism (`can_be_disabled`).
- **`ConditionContainer`** → `UserContainerRules` (item containment) + an `operator` enum child on `ConditionManager` and `ConditionGroup`.
- **`InputValueCondition`** → current `NumberCompareCondition` and `BoolCondition` are Phase-3 starting points with the same source-reference / comparator / reference pattern.

## Assessment

Your model is directionally correct. I would keep the four user-facing condition families:

1. **Input Value Condition**
2. **Input Node Condition**
3. **Condition Group**
4. **Script Condition**

The main architectural correction I would make is this:

> **`ConditionManager` and `ConditionGroup` should not be two separate mechanisms. They should be the same recursive condition-container model used in two roles.**

The root **ConditionManager** is the fixed condition container owned by an Action processor. A **ConditionGroup** is a user-created condition node that contains its own local condition container. To the parent, the group behaves exactly like a single condition.

This fits the revised architecture because conditions are components of the Action formula, not formula families; `ConditionsManagerANode` is a Managed ANode; and all visible condition-related concepts should be `golden_core::Node`s, not parallel inspector DTOs. 

It also fits the repo direction: `src/state_machine/` owns Chataigne state-machine policy, while reusable Alchemist/statechart behavior lives under shared Golden crates/submodules. ([GitHub][1]) The repo rules also explicitly favor clean architecture, removing duplicated concepts, and fixing ownership at the correct boundary. ([GitHub][2])

# Detailed Plan: Conditions for Chataigne2

## 1. Final conceptual model

```text
ActionStateProcessor
  └─ ConditionManagerNode
      ├─ InputValueConditionNode
      ├─ InputNodeConditionNode
      ├─ ScriptConditionNode
      └─ ConditionGroupNode
          ├─ InputValueConditionNode
          ├─ InputNodeConditionNode
          └─ ConditionGroupNode
```

The key invariant:

```text
A ConditionManager contains conditions.

A ConditionGroup is itself a condition,
but internally it also contains conditions.

Both use the same container/reducer logic.
```

So the runtime view becomes:

```text
Condition leaf
  -> raw boolean
  -> common condition post-processing
  -> valid / invalid output

Condition group
  -> evaluate child conditions
  -> reduce children with AND / OR / N-of-M / etc.
  -> apply group-level post-processing
  -> valid / invalid output

Root condition manager
  -> evaluate direct child conditions
  -> reduce direct child conditions
  -> apply manager-level post-processing
  -> final valid / invalid output for the Action processor
```

# 2. Terminology

## Condition

A **Condition** is anything that can output a validity state.

It can be a leaf:

```text
Input Value Condition
Input Node Condition
Script Condition
```

Or a composite:

```text
Condition Group
```

A condition should not directly trigger commands, launch sequences, change states, or produce side effects. It only contributes a validity result.

---

## ConditionManager

The **ConditionManager** is the fixed root condition container generated by an Action processor.

It is not user-created from the processor level.

It owns:

```text
child conditions
condition combination mode
empty policy
diagnostics
root-level validation / invalidation / toggle behavior
```

It outputs the final boolean validity of the Action processor’s condition section.

---

## ConditionGroup

A **ConditionGroup** is a user-created condition that contains children.

It is both:

```text
a condition as seen by its parent
a local condition manager for its children
```

This is the important unification.

Internally:

```text
ConditionGroupNode
  └─ ConditionContainer
      ├─ child condition
      ├─ child condition
      └─ child group
```

Externally:

```text
Parent ConditionManager sees the group as one condition.
```

---

## ConditionContainer

A **ConditionContainer** is the reusable internal mechanism shared by `ConditionManager` and `ConditionGroup`.

It owns:

```rust
pub struct ConditionContainer {
    pub operator: ConditionReduceOperator,
    pub empty_policy: EmptyConditionPolicy,
    pub disabled_policy: DisabledConditionPolicy,
    pub error_policy: ConditionErrorPolicy,
    pub children: Vec<NodeId>,
}
```

Recommended operators:

```rust
pub enum ConditionReduceOperator {
    All,
    Any,
    None,
    AtLeast { count: usize },
    Exactly { count: usize },
    CustomExpression, // later
}
```

Default should be:

```text
All
```

Default empty policy should be:

```text
Invalid
```

Even though logical `AND` over an empty set is mathematically true, for Chataigne UX this would be dangerous because an empty Action condition manager could accidentally fire.

# 3. Common condition behavior

All condition types, including groups, should share a common base.

```rust
pub struct ConditionCommon {
    pub enabled: bool,
    pub invert: bool,
    pub temporal: ConditionTemporalPolicy,
    pub context_policy: ConditionContextPolicy,
    pub label_policy: ConditionLabelPolicy,
}
```

This prevents duplicating validation time, invalidation time, toggle behavior, inversion, diagnostics, and context handling across every condition type.

---

## Temporal behavior

Every condition has:

```rust
pub struct ConditionTemporalPolicy {
    pub validation_delay_ms: f64,
    pub invalidation_delay_ms: f64,
    pub output_mode: ConditionOutputMode,
}
```

Recommended output modes:

```rust
pub enum ConditionOutputMode {
    Normal,
    ToggleOnValidEdge,
    ToggleOnInvalidEdge,
    PulseOnValidEdge { duration_ms: f64 },
    PulseOnInvalidEdge { duration_ms: f64 },
}
```

Processing order should be:

```text
1. Evaluate raw source condition.
2. Apply invert.
3. Apply validation / invalidation delay.
4. Apply toggle / pulse output mode.
5. Emit final condition state.
```

This is preferable to toggling on raw input changes because it avoids unstable toggles caused by noisy values.

---

## Runtime state per condition per context lane

Because processors may run across multiple context lanes, each condition needs lane-local memory.

```rust
pub struct ConditionRuntimeState {
    pub last_raw: Option<bool>,
    pub last_logical: Option<bool>,
    pub stable_valid: bool,
    pub pending_target: Option<bool>,
    pub pending_since_ms: Option<f64>,
    pub toggled_value: bool,
    pub last_transition_ms: Option<f64>,
    pub last_eval_ms: Option<f64>,
}
```

For multiplexed execution:

```text
same condition node
same authored configuration
different runtime state per ContextFrame
```

This matches the broader architecture where one compiled formula can run across many context lanes with independent memory per lane.

# 4. Condition output model

A condition should not output only `bool`.

It should output a structured evaluation result.

```rust
pub struct ConditionEval {
    pub validity: ConditionValidity,
    pub raw_value: Option<ParamValue>,
    pub logical_value: Option<bool>,
    pub final_value: bool,
    pub diagnostic: Option<ConditionDiagnostic>,
}
```

```rust
pub enum ConditionValidity {
    Valid,
    Invalid,
    PendingValid,
    PendingInvalid,
    Disabled,
    Unknown,
    Error,
}
```

The parent reducer can reduce `final_value`, while the inspector/debugger can show the richer `validity`.

This gives better UX:

```text
Condition: OSC module connected
Status: Pending valid, 324 ms / 500 ms

Condition: Fader > 0.5
Status: Invalid
Current value: 0.31

Condition: Script condition
Status: Error
Reason: missing variable "clip_name"
```

# 5. Input Value Condition

## Purpose

An **Input Value Condition** reads any value from a `ParameterNode` or compatible parameter source, projects it if needed, and compares it against a user-defined reference value.

Examples:

```text
Button A == true
Fader 1 > 0.5
Vec2 joystick magnitude > 0.8
Color luminance < 0.2
Color red channel > 0.7
Enum mode == "armed"
String contains "go"
```

---

## Data model

```rust
pub struct InputValueConditionNode {
    pub common: ConditionCommon,
    pub source: ParameterValueSourceRef,
    pub projection: ValueProjection,
    pub comparator: ValueComparator,
    pub reference: ParamValue,
}
```

---

## Source reference

```rust
pub struct ParameterValueSourceRef {
    pub node_ref: NodeRef,
    pub parameter_path: ParameterPath,
}
```

This should reference existing Golden Core node/parameter identity, not stringly typed paths where avoidable.

---

## Projection

Compound values should support explicit projection.

```rust
pub enum ValueProjection {
    Whole,

    BoolValue,

    NumberValue,

    Vec2Magnitude,
    Vec2X,
    Vec2Y,

    Vec3Magnitude,
    Vec3X,
    Vec3Y,
    Vec3Z,

    ColorLuminance,
    ColorRed,
    ColorGreen,
    ColorBlue,
    ColorAlpha,

    EnumValue,
    StringValue,
}
```

Default projection should be type-dependent:

```text
Float / Int       -> NumberValue
Bool              -> BoolValue
Vec2 / Vec3       -> Magnitude
Color             -> Luminance
Enum              -> EnumValue
String            -> StringValue
```

For vectors and colors, the user can switch from default projection to component projection.

  ==

# 6. Input Node Condition

## Purpose

An **Input Node Condition** lets a node type expose higher-level condition endpoints.

This is important because many useful conditions are not simple parameter comparisons.

Examples:

```text
Module is connected
Module has error
OSC module received a message in the last 2 seconds
MIDI device is available
Serial device has unread data
Video module frame rate is above threshold
Timeline is playing
Sequence is currently running
```

Your proposal is right: this avoids forcing users to manually build intricate low-level conditions when a module already knows how to compute the answer.

---

## Design rule

Node types should expose conditions through a declarative provider registry.

```rust
pub trait NodeConditionProvider {
    fn condition_endpoints(
        &self,
        ctx: &ConditionProviderCtx,
        node: NodeId,
    ) -> Vec<ConditionEndpointDeclaration>;

    fn evaluate_condition_endpoint(
        &self,
        ctx: &ConditionEvalCtx,
        node: NodeId,
        endpoint: ConditionEndpointId,
        params: &ConditionEndpointParams,
    ) -> ConditionEvalResult;
}
```

---

## Endpoint declaration

```rust
pub struct ConditionEndpointDeclaration {
    pub id: ConditionEndpointId,
    pub label: String,
    pub description: String,
    pub output: ConditionEndpointOutput,
    pub parameters: Vec<ConditionEndpointParameter>,
    pub default_temporal_policy: ConditionTemporalPolicy,
}
```

```rust
pub enum ConditionEndpointOutput {
    Bool,
    Value { value_type: ValueTypeId },
    Event,
}
```

This matters for something like:

```text
OSC time since last message received
```

That endpoint may naturally output a duration, not a boolean. The condition UI can then expose:

```text
Time since last message received < 2 seconds
```

So `InputNodeCondition` and `InputValueCondition` share comparator infrastructure where possible.

---

## Input Node Condition data model

```rust
pub struct InputNodeConditionNode {
    pub common: ConditionCommon,
    pub provider_node: NodeRef,
    pub endpoint_id: ConditionEndpointId,
    pub endpoint_params: ConditionEndpointParams,
    pub comparator: Option<ValueComparator>,
    pub reference: Option<ParamValue>,
}
```

Rules:

```text
Bool endpoint:
  comparator/reference may be omitted.

Value endpoint:
  comparator/reference required.

Event endpoint:
  interpreted through event policy:
    happened this tick
    happened within duration
    count within duration
```

---

## Boundary rule

Generic `golden_alchemist` should not know about OSC, MIDI, DMX, modules, serial devices, or Chataigne-specific endpoints. Those condition providers belong in Chataigne integration crates/layers, consistent with the revised crate split and repo boundary rules.

# 7. Script Condition

## Purpose

A **Script Condition** gives expert users full control when built-in condition types are insufficient.

It should be a condition node with a script body and explicit condition output.

```rust
pub struct ScriptConditionNode {
    pub common: ConditionCommon,
    pub script: ScriptSource,
    pub script_api_policy: ScriptConditionApiPolicy,
}
```

The script should be able to:

```text
read current context
read parameter values
read selected node state
use local script memory
set condition valid / invalid
set diagnostic message
```

It should not directly dispatch commands or mutate unrelated state. Conditions should remain pure from the Action runtime’s point of view.

---

## Script API shape

Conceptually:

```rust
pub struct ScriptConditionOutput {
    pub valid: bool,
    pub reason: Option<String>,
}
```

Example user script behavior:

```text
valid = osc.connected && last_message_age < 2.0 && current_scene == "intro"
```

Runtime should expose:

```text
ctx.current_context()
ctx.param(path)
ctx.node_state(node_ref)
ctx.now()
ctx.memory()
ctx.set_valid(bool)
ctx.set_reason(string)
```

---

## Runtime rule

Script conditions need the same per-lane runtime memory model as other conditions.

```text
ScriptConditionNode + ContextFrame -> ScriptConditionRuntimeState
```

This avoids one lane toggling or stabilizing another lane by accident.

# 8. Condition Group

## Purpose

A **Condition Group** is the user-facing way to structure nested condition logic.

Example:

```text
Conditions
  All:
    Group: Safety OK
      All:
        Emergency stop is false
        Lighting desk connected
        OSC heartbeat age < 2s

    Group: Trigger
      Any:
        MIDI Button A pressed
        OSC /go received
        Dashboard Launch button pressed
```

The root manager sees:

```text
Safety OK == valid
Trigger == valid
```

Then combines them with its own operator.

---

## Data model

```rust
pub struct ConditionGroupNode {
    pub common: ConditionCommon,
    pub container: ConditionContainer,
}
```

The group has its own:

```text
enabled
invert
validation delay
invalidation delay
toggle behavior
operator
empty policy
diagnostics
```

This is powerful because users can stabilize or toggle an entire group, not only individual leaves.

# 9. Reducer behavior

A condition container combines direct child outputs only.

```text
Container does not flatten nested groups.
A group is reduced locally, then passed upward as one condition.
```

Recommended reducer semantics:

```rust
pub enum ConditionReduceOperator {
    All,
    Any,
    None,
    AtLeast { count: usize },
    Exactly { count: usize },
    CustomExpression,
}
```

## All

```text
valid if every enabled direct child is valid
```

## Any

```text
valid if at least one enabled direct child is valid
```

## None

```text
valid if no enabled direct child is valid
```

## AtLeast

```text
valid if at least N enabled direct children are valid
```

## Exactly

```text
valid if exactly N enabled direct children are valid
```

## CustomExpression, later

Example:

```text
safety && (button || osc_go) && !blackout
```

This should be a later phase, not part of the first implementation.

# 10. Disabled, unknown, and error policy

You need explicit policy here. Otherwise nested groups become ambiguous.

```rust
pub enum DisabledConditionPolicy {
    Ignore,
    TreatAsInvalid,
    TreatAsValid,
}
```

Recommended default:

```text
Ignore
```

```rust
pub enum ConditionErrorPolicy {
    TreatAsInvalid,
    BlockAndReport,
}
```

Recommended default:

```text
TreatAsInvalid
```

For live-show software, a failed condition should usually not accidentally validate an Action.

```rust
pub enum UnknownConditionPolicy {
    TreatAsInvalid,
    KeepLastKnown,
}
```

Recommended default:

```text
TreatAsInvalid
```

`KeepLastKnown` can be useful for advanced cases, but it should be explicit.

# 11. Context and multiplex behavior

Conditions must be context-aware from the start.

A ConditionManager should evaluate per `ContextFrame`.

```text
ContextSet:
  lane 1: fixture = spot_01
  lane 2: fixture = spot_02
  lane 3: fixture = spot_03

ConditionManager output:
  lane 1: valid
  lane 2: invalid
  lane 3: valid
```

Then the Action formula branches per lane:

```text
valid lane   -> consequences when true, contextual intents
invalid lane -> consequences when false, contextual intents
```

This preserves the architecture where multiplexed execution is produced by context dimensions, not by a special Multiplex formula. 

For transitions, the existing broader design still applies:

```text
Global
PerContext
AnyContext
AllContexts
```

So a condition manager can feed either per-lane Action behavior or higher-level transition guards, depending on the owning formula/statechart usage.

# 15. Runtime evaluation pipeline

Per tick, per active processor, per context lane:

```text
1. Resolve active ContextSet.
2. For each ContextFrame:
   1. Evaluate root ConditionManagerNode.
   2. Recursively evaluate child condition nodes.
   3. Apply child temporal policies.
   4. Reduce groups locally.
   5. Apply group temporal policies.
   6. Reduce root manager.
   7. Apply root temporal policy.
   8. Emit final condition state for this lane.
3. Feed final condition state into Action formula branch.
4. Collect contextual intents.
5. Arbitrate and dispatch side effects.
```

No condition should directly perform side effects. The broader architecture already states that ANodes should emit intents and that dispatch happens after runtime collection/arbitration.

# 19. Final recommended architecture

```text
Conditions are nodes.

ConditionManager is the fixed root condition container for an Action processor.

ConditionGroup is a condition node that owns the same local container mechanism.

InputValueCondition reads a parameter value, projects it, and compares it.

InputNodeCondition calls a condition endpoint exposed by a node type.

ScriptCondition evaluates user script and outputs valid / invalid.

All conditions share enabled, invert, validation delay, invalidation delay, toggle/output mode, context policy, and diagnostics.

All condition runtime state is per context lane.

Condition containers reduce only their direct children.

Nested groups are evaluated locally and exposed upward as one condition.

Condition lowering produces compare/reducer/temporal graph fragments inside the Action formula.

No condition performs side effects directly.

No parallel condition DTO inspector is introduced.

The standard Golden Core node tree remains the source of truth.
```
